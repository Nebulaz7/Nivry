# NFT-controlled agent authority: OutLayer and standards

Researched 2026-11-06. **Scope:** provider-specific authority/revocation and standards precedent; NEAR access-key and NFT-core analysis is being checked separately. Public documentation/source reads only: no registration, authentication, wallet actions, paid calls, or live revocation tests. `PLAN.md` was not edited.

**Evidence labels:** **Documented** = first-party statement, not independently verified deployment behavior; **Code** = inspected public source, not proof of deployed bytecode; **Inference/recommendation** = proposed Nivry design, not an existing provider feature.

## Bottom line

- **An NFT transfer alone does not establish complete NEAR wallet authority.** OutLayer's custody policy controller, API authentication, bound asset-account grants, and sovereign-vault recovery authority are separate mechanisms. No documented generic feature makes all of them follow an arbitrary NEP-171 token. A purpose-built controller/account can make NFT ownership govern its permissions, but exclusivity requires closing every other authority path. [1–7]
- **An NFT contract can plausibly be the stable custody-policy controller from inception.** The policy contract records the first caller (`predecessor_account_id`) as controller; it does not require that caller to be a human/keyed wallet. A Nivry contract could authorize its calls by token ownership. **This is code-level feasibility, not documented turnkey NFT integration.** The controller cannot simply be replaced with each successive token owner through the inspected API. [5]
- **OutLayer already has a relevant NFT/account integration, but not the desired universal handoff.** House of Stake (`hos_lease`) clears grants on ownership rotation and terminates the old binding. It is documented as testnet-exercised, with mainnet not open. The underlying leased wallet structurally forbids several native account actions, and transfers sweep supported balances to the outgoing owner. [3,4,8]
- **Prefer a separate Contract Standards NEP depending on NEP-171, not a normative expansion of every NFT's core semantics.** NEP-1 explicitly prefers a separate NEP for a separately meaningful extension. ERC-6551 and agent-registry proposals provide precedent for layering account/agent interfaces around existing NFTs. This is a recommendation, not an assigned or approved NEP. [9–13]

## 1. Existing custody wallet: what “controller” actually means

**Documented:** A custody wallet's Agent ID is a TEE-derived public key; its API key authenticates operations. The custody wallet has its own implicit NEAR account. Its encrypted on-chain policy is keyed by wallet public key. A binding adds a distinct **asset account**, while the custody wallet remains the **executor**, paying gas. Binding is neither a wallet rename nor transfer of its credentials, secrets access, billing, or balances. [1,2,4]

**Code — `contract/src/wallet.rs`:** [5]

- `store_wallet_policy` verifies a wallet-key signature covering `store_wallet_policy:v1:{wallet_pubkey}:{len}:{encrypted_data}:{caller}` and a storage deposit. On first creation it saves `owner = predecessor_account_id`.
- Subsequent updates require **the same original controller**, plus another valid wallet signature. `freeze_wallet`, `unfreeze_wallet`, and `delete_wallet_policy` require the controller as predecessor; freeze/unfreeze do not require a wallet signature. A policy update preserves an existing freeze.
- No controller-transfer method exists in this inspected policy module. Updating the encrypted approver list is not changing `WalletPolicyEntry.owner`. `storage_refund_to` changes storage-refund entitlement, not control.

**Inference for Nivry:** A stable NFT/controller contract can be that first predecessor, relay prepared policy payloads, and gate updates/freezes on its own token-owner/epoch checks. Merely passing an NFT contract ID as an argument is insufficient: the call must actually originate from it. OutLayer never queries NFT ownership in this module. The contract account would need adequate funds and custom authorization logic; a multi-token controller must bind each wallet to the correct token.

For a policy already owned by Alice, Bob cannot update/freeze it merely because Alice sold the NFT. Deleting and recreating the policy is **not a safe ownership-transfer primitive**: it needs Alice's cooperation, creates an unrestricted-policy interval, and a new store needs a fresh caller-bound wallet signature. Do not assume that an existing randomly registered wallet can be converted into an NFT-authenticated deterministic wallet while keeping its identity. Deterministic identities depend on `(account_id, seed, vault scope)` and require a full-access ed25519 signature, not proof of NFT ownership. [1,5,6]

**Contract-owner authentication caveat:** OutLayer accepts contract-based *approval votes* only for wallet builds its deployment recognizes, using `w_is_signature_allowed` and `w_resolve_auth`, with no pinned approver pubkey. This does **not** document support for an arbitrary NFT contract as an approver or as a `Bearer near:` authenticator. Generic contract-based auth would need provider support/allowlisting or a separate adapter. [1,4]

## 2. Binding precedent and exact revocation boundaries

| Authority/path | Documented mechanism | Exact limitation relevant to sale/handoff |
| --- | --- | --- |
| Custody `wk_` delegate credential | `DELETE /wallet/v1/api-key/{key_hash}` | **409 if it is the last active key for that wallet.** Docs do not establish a non-destructive atomic revoke-all-and-reissue operation, complete key enumeration, a `wk_` revocation propagation SLA, or recursive child-wallet revocation. The delegate-creation flow derives a **sub-wallet**; do not assume it adds a replacement credential to the original random wallet. [1,6] |
| Deterministic-wallet NEAR authentication | Remove the old full-access key from the authenticating NEAR account | Revocation **within 60 seconds**, due to cache TTL. Rotating this NEAR key is separate from deleting existing `wk_` delegates; no automatic cascade is documented. Moving the NFT changes neither. [1,6] |
| Personal bound account executor | Owner removes executor from the account's extension set; code removal/redeployment also ends supported access | OutLayer documents the lane stopping **within five seconds** (cached allow; denials not cached). This revokes the asset-account lane, **not** the executor's own custody wallet/API key or other grants. Original owner keys remain able to sign directly throughout personal binding. [2,4] |
| OutLayer binding record and pending approvals | `DELETE /wallet/v1/binding` | Ends OutLayer's side and cancels approvals waiting on that account; it is **not documented as removing the on-chain extension/grant**. For durable revocation, remove the actual on-chain permission too. [2,4] |
| Leased-account executor | Revoke on-chain grant, expire lease, or rotate ownership | Grant revocation/expiry stops the lane within **five seconds**; a lifecycle webhook invalidates the cached observation for the next call. Webhook body is only a hint: OutLayer rereads chain state, so `event: revoked` cannot itself revoke authority. [3,4] |
| Leased-account ownership rotation | Grants cleared; binding pinned to owner and rotation sequence/implementation epoch | Old binding **terminates rather than following the buyer**; a new grant/binding is needed. Migration under unchanged ownership can repin an epoch; a different owner ends the binding in any epoch. This is not automatic buyer control of the old custody wallet. [3,4] |
| Custody policy freeze | Controller calls `freeze_wallet` on chain | Stops new policy-governed signing, not credential destruction. **Contract pause blocks freeze writes while signing can continue.** No wall-clock freeze propagation bound was established here. [1,7] |
| Resting limit orders | Explicit cancellation, including `cancel-all` after freeze | Freeze **does not cancel resting orders**: already-authorized payouts can happen later. Cancellation is asynchronous; `pending_cancel` may still fill; only `is_payout_status_final` establishes completion. [1] |
| Wallet deletion | `/wallet/v1/delete` deletes NEAR account and revokes all API keys | Destructive, not ownership transfer. Only native NEAR goes to beneficiary; docs warn FT/Intents balances are lost unless moved first. [1] |
| Sovereign-vault recovery | Parent finalizes recovery, replacing OutLayer's keys on the **vault account** | Parent can recover the master and every wallet key under it: **1–30 day unilateral window**, or **7-day DAO cessation delay**. It does not rotate derived wallet keys. Removing vault keys is not deleting each wallet's account keys, nor making an NFT owner the recovery parent. [7] |

**API-key enforcement nuance (Code + documented trust model):** `authorized_key_hashes` is an on-chain encrypted policy field exposed by the API, but the shared TEE `Policy` parser explicitly ignores it. OutLayer says its coordinator's readable policy copy handles authorized key hashes; the enclave relies on the coordinator to authenticate the request and identify the wallet. Therefore API-key revocation is not equivalent to cryptographic destruction/rotation of the wallet's TEE signing key. The public OpenAPI snapshot also omits the documented delegate-key routes, so exact authorization, inventory and rotation behavior needs provider confirmation rather than extrapolation from the schema. [6,7,14]

**Inference:** A handoff cannot undo already executed transfers, already emitted signatures, external sessions, token approvals or other standing authorizations. The explicit resting-order limitation proves that “stop signing now” is insufficient even within OutLayer. A Nivry sale protocol must define in-flight requests, pending approvals, signed artifacts and delegated permissions—not promise retroactive cancellation.

## 3. House of Stake / NEAR Accounts: useful, constrained precedent

**Documented by both sides:** OutLayer's lease mode uses an executor in the keyless asset account's control set plus an on-chain spend grant. Its grant permits only named `transfer`, `ft_transfer`, and `nft_transfer` operations, with budgets, recipients, token-ID fences, expiry and balance reserve. It rejects account rewiring even if custody policy allows it. [3,4]

NEAR Accounts describes NEP-171 name tokens plus `tla-registry → hos-extension → hos-wallet` authority. Registry and wallet ownership records must agree; only the registry can invoke the extension's `force_transfer`. The underlying wallet's external action set is `Transfer`, `FunctionCall`, `DeterministicStateInit`—**not `AddKey`, `DeleteKey`, `DeleteAccount`, or `DeployContract`**. This is structural, not a configurable spending policy. [8]

**Crucial mismatch with “agent and treasury travel together”:** On normal ownership change, supported NEAR/FT balances are swept to the **outgoing** owner's payout account; NFTs and assets in other contracts are not automatically swept. Leases also have expiry/reclaim and separate recovery authority. This is evidence that account control can be represented by an NFT, **not** evidence that all wallet assets, rights and provider credentials transfer unchanged or exclusively to the buyer. OutLayer's verifier takes leased ownership from `nft_item_info.owner_id`; the registry's `nft_token` check establishes that it minted the name, not an ownership comparison. Nivry must specify its own authoritative state and synchronization rules. [4,8]

## 4. Standard precedent and recommended scope

- **NEP-1 (current text, updated 2025-08-04):** reusable contract interfaces belong in a Contract Standards NEP. Start with prior-proposal search and a public issue, gather community feedback, then submit a draft using the template and PR-assigned number. The lifecycle is Draft → Review → Voting → Approved/Rejected. Approved standards are generally final; maintenance allows exceptional extensions, but explicitly says a separately meaningful extension is better submitted as a new dependent NEP. **The repository README still describes an older Last Call process; prefer NEP-1 itself.** [9]
- **Existing NEAR modular precedent:** NEP-171, metadata 177, approval 178, enumeration 181, royalties 199 and events 256 are separately numbered standards. Targeted searches of the official NEPs index and GitHub issues/PRs for `agent`, `token-bound`, and `6551` did not locate a dedicated accepted NFT-bound-agent/account NEP. This is a search result, **not proof no proposal exists**. The older account-extensions discussion #478 is closed/retracted, not an adopted NFT-wallet standard. [10]
- **NEP-641, Final:** `w_resolve_auth` supplies contract-defined, off-chain authorization, including keyless accounts and delegation. It is relevant to provider/login/approval interoperability, but explicitly **must not gate on-chain transactions** (no stateful replay protection). Full-access keys take precedence; contract-only authority requires removing them. OutLayer's supported contract votes are narrower than this generic standard. [4,11]
- **ERC-6551:** separate registry/account interfaces layer token-bound accounts around existing NFTs **without changing ERC-721**. The reference account resolves authority through current `ownerOf`. The spec permits additional signers and discusses ownership cycles and seller asset-draining fraud: it is not a universal promise of exclusive owner access or safe treasury sale. Ethereum-specific, not directly implementable as a synchronous NEAR ownership lookup. [12]
- **ERC-8004:** transferable ERC-721 agent discovery/identity is separate from wallet ownership. Its reserved `agentWallet` payment address is **cleared on transfer and must be reverified**, rather than transferring wallet authority. [13]
- **ERC-8171 agent registry:** first-party author draft in open, unmerged ERCs PR #1559; it proposes agent/NFT binding without editing ERC-721. Its draft says NFT ownership is authoritative, but also says no automatic transfer callbacks and explicit new-owner interaction is needed. Useful design discussion, **not a finalized standard or proof of credential revocation**. The canonical master file returned 404; the cited author-branch snapshot was read instead. [15]

**Recommendation, not an existing specification:** Standardize a small optional token-bound-account/agent-authority interface: immutable `(network, NFT contract, token_id, account/controller)` binding; discoverable execution capabilities and exclusions; owner/authority epoch; transfer/transfer-call rollback semantics; delegate invalidation; replay and asynchronous callback checks; freeze/handoff state; recovery/upgrade authorities; burn behavior; and finality of revocation. Separate **identity**, **account execution**, and **provider credentials**. Treat OutLayer as an adapter with explicit capability declarations, not a universal NEP implementation. Avoid requiring ordinary NEP-171 transfers to perform opaque off-chain API-key operations.

## 5. What remains unproven / provider questions

1. Can a contract-controlled policy be provisioned end-to-end for an **existing** wallet through supported APIs/UI? Is a safe direct controller-transfer operation planned? Public policy code does not supply one.
2. How can the new owner enumerate and revoke **every** old credential (including the original registration key and descendants), install a replacement on the **same wallet**, and verify completion? What authenticates revocation, and what is its cache/in-flight bound? Last-active-key `409` prevents assuming “delete everything”.
3. Is arbitrary NFT-contract/NEP-641 owner authorization supported, or only the explicitly allowlisted EIP-712/passkey wallet builds? Who approves new builds/decoders?
4. Which deployed hashes/network releases match the inspected sources? OutLayer's current web docs call personal binding live, while repository `NON_CUSTODIAL.md` still says personal binding/vault mainnet release is pending. Lease mainnet is explicitly not open in Agent Connect. No deployment state was independently checked.
5. “Complete/exclusive” remains conditional on infrastructure governance. OutLayer's own `NON_CUSTODIAL.md` discloses a DAO full-access key capable of obtaining the shared master outside an enclave, one-member/owner build approval, and key-controlled upgrades without vote/delay. Sovereign-vault recovery leaves the same master/addresses and cannot erase previously learned keys. Marketing claims that nobody can extract keys must be read with these explicit qualifications. [7]
